# igOS TPM-PKI Integration — Design Sketch

Status: **Design — no code yet (2026-11-09)**

Scope: fold TPM-backed private keys into the normal `pki` configuration tree so
operators do **all** PKI work in **one place**, whether a key is held in software
or sealed in the TPM. TPM stops being a global, reboot-gated *mode* with its own
parallel key store and becomes a per-key **storage attribute**
(`storage software | tpm`). The TPM is treated as always-present hardware; there
is no enable/disable. This is a **greenfield** redesign for igOS — there is no
deployed TPM-PKI configuration to preserve, so **no migration** is required.

A related but deliberately **separate** concern — the per-unit, factory-
provisioned **device identity (DevID)** used to authenticate to the igOS cloud —
is covered in §3.11; it is intentionally kept independent of the operator `pki`
tree.

This is the counterpart to `docs/igos-fips-140-3-design.md`: FIPS already set the
precedent that a security capability belongs in the **configuration** (`set
system option fips`), applied by commit, visible in `show configuration`, and
enforced per-feature — not hidden behind an out-of-band op-mode toggle.

---

## 1. Motivation — what's wrong with the current model

Two structural problems, both confirmed in the code (2026-11-09):

### 1.1 Activation is an out-of-band op-mode toggle that forces a reboot

- `tpm enable` / `tpm disable` (`op-mode-definitions/tpm.xml.in`) call
  `src/op_mode/tpm.py`, which in `python/vyos/tpm.py` just `touch`/`rm` a flag
  file `/run/tpm-state/boot/.tpm.enabled` on a mounted persistent partition and
  then **unconditionally reboot** the box.
- That state lives **outside the configuration tree**: invisible to `show
  configuration`, never written to `config.boot`, not diffable, not captured in a
  backup, not restored when a config is loaded onto another unit.
- The reboot is **not** a hardware or crypto requirement. The TPM is a passive
  chip that measures boot state into PCRs on every boot regardless of any VyOS
  setting; `tpm_enable()` performs no crypto and touches no hardware. Every
  consumer of the flag is a **conf-mode (commit-time)** script — so the reboot
  exists only to force the normal boot-time config replay to re-run those
  scripts and restart dependent services. A commit could do the same live.

### 1.2 Key management is a parallel store keyed off a hidden global flag

- TPM keys are generated by `generate tpm …` (op-mode) and written as **files**
  under `/config/auth/tpm/…` (`python/vyos/tpm_pki.py` → `TPM_PKI_ROOT_PATH =
  /config/auth/tpm`), **not** as `pki` config nodes.
- Consumers branch on the global `tpm_enabled()` flag. In
  `src/conf_mode/interfaces_openvpn.py`, when `tpm_enabled()` it **ignores the
  `pki certificate` tree entirely** and reads
  `/config/auth/tpm/cert/<name>/<name>.pem|.key` instead; otherwise it uses the
  normal PKI nodes. `src/conf_mode/service_ssh.py` and `src/conf_mode/serial.py`
  branch the same way.
- The tell is `src/completion/list_pki_with_tpm.py`: the **same** CLI completion
  returns TPM-store names when `tpm_enabled()`, and `pki certificate` names
  otherwise.

Net effect: the same config reference (`certificate foo`) silently resolves to a
**different backing store** depending on a reboot-persisted flag that is not in
the config. Two parallel universes, non-local reasoning, no single source of
truth, and config portability quietly breaks.

### 1.3 Who actually needs "TPM at boot"? (grounding the greenfield claim)

The only consumer of the PCR-sealed key primitives (`write_tpm_key` /
`read_tpm_key` / `clear_tpm_key` in `python/vyos/tpm.py`) is **disk/config
encryption** (`src/helpers/vyos-config-encrypt.py`), which seals the `/config`
volume key to PCRs `0,2,4,7` and unseals it in early boot to mount the encrypted
volume. That feature:

- is a **system disk-encryption** concern, not a PKI object the operator
  manages;
- **does not use the `.tpm.enabled` flag** — it checks `/sys/class/tpm/tpm0`
  directly and has its own enable flow;
- never touches the `pki` tree.

Everything else TPM-related is **config/commit-driven**, not early-boot:
OpenVPN/SSH/serial PKI objects (the `tpm_pki` store) and the WireGuard
file-wrapped private key (`src/op_mode/pki.py` `write_tpm_key_file` ↔
`src/conf_mode/interfaces_wireguard.py` `read_tpm_key_file`). The installer
(`src/op_mode/image_installer.py`) only *copies* the TPM state dir on upgrade; it
seals nothing.

**Conclusion:** the global enable/disable flag serves no early-boot or non-config
purpose. It exists solely to flip the conf-mode PKI consumers between the two
stores. Remove it; make TPM a per-key attribute. Disk encryption is orthogonal
and stays exactly as-is.

## 2. Goal & principles

1. **One place for PKI.** An operator configures `pki certificate`, `pki
   key-pair`, and `pki ca` the same way regardless of where the private key
   lives. TPM is a property of the key, surfaced as `storage tpm`.
2. **No global mode, no reboot.** The TPM is always present. There is no
   enable/disable; changes apply on commit like any other config.
3. **Secrets never in config.** A `storage tpm` key's private material stays
   sealed in the TPM; `config.boot` carries only the public certificate and the
   `storage tpm` reference. (This is strictly *better* than software keys, whose
   PEM is in the config.)
4. **Single source of truth.** Consumers resolve a `pki` node and read its
   `storage`; they never consult a hidden global flag. CLI completion is unified.
5. **Explicit FIPS boundary.** TPM key operations ride the same OpenSSL provider
   path as everything else, so FIPS reasoning is per-key and explicit (see
   `igos-fips-140-3-design.md` §6.1).

## 3. Design

### 3.1 Schema — `storage` on the `private` node

New include `interface-definitions/include/pki/private-key-storage.xml.i`:

```xml
<leafNode name="storage">
  <properties>
    <help>Backing store for the private key</help>
    <completionHelp><list>software tpm</list></completionHelp>
    <valueHelp>
      <format>software</format>
      <description>Private key stored in the configuration (PEM)</description>
    </valueHelp>
    <valueHelp>
      <format>tpm</format>
      <description>Private key sealed in the TPM; not present in the configuration</description>
    </valueHelp>
    <constraint><regex>(software|tpm)</regex></constraint>
  </properties>
  <defaultValue>software</defaultValue>
</leafNode>
```

Wired into the three asymmetric key holders in
`interface-definitions/pki.xml.in`:

- `pki certificate <name> private` (currently ~line 111)
- `pki key-pair <name> private` (~line 155)
- `pki ca <name> private` (~line 19) — **CA signing key in the TPM is a primary
  use case; included.**

Left out: `pki openssh`, `pki dh`, `pki openvpn shared-secret` — not
TPM-sealable asymmetric keys.

### 3.2 Semantics

- `storage software` (default) → unchanged behavior: the existing `private key
  <base64 PEM>` leaf
  (`interface-definitions/include/pki/cli-private-key-base64.xml.i`) holds the
  key.
- `storage tpm` → the `private key` leaf is **absent**. The public
  `certificate` leaf still lives in the node, so the certificate is in config and
  portable. `src/conf_mode/pki.py` `verify()` enforces:
  - `storage tpm` ⇒ no `private key` set (mutually exclusive), and
  - `password-protected` is rejected under `storage tpm` (meaningless for a
    sealed key).

### 3.3 Binding — name-as-alias

The tagNode **name** *is* the TPM object alias: `pki certificate foo private
storage tpm` binds to the TPM object `foo`. One-to-one, zero extra config, and it
matches how the current store already keys blobs by name
(`/config/auth/tpm/.../<name>`). An explicit `tpm-handle` / `tpm-index` leaf for
advanced persistent-handle control is a possible later addition, not part of the
initial design.

### 3.4 Generation — one command, a flag

Fold TPM into the existing `generate pki …` flow (which already prints `set`
commands for the operator to apply). For example:

```
generate pki certificate <name> … storage tpm
```

seals the key into the TPM (under alias `<name>`) and emits:

```
set pki certificate <name> private storage tpm
set pki certificate <name> certificate <base64 public cert>
```

instead of a base64 private key. The legacy `generate tpm …` op-mode path is
removed.

### 3.5 Consumers — resolve the node, not a global flag

Every `if tpm_enabled(): <parallel path>` is replaced by: resolve the referenced
`pki` node and read `private storage`. If `tpm`, hand the service its TPM-backed
key:

- **OpenVPN / serial / stunnel** — via the OpenSSL tpm2 provider path.
- **sshd** — via `ssh-tpm-agent` with the sealed host key.
- **strongSwan / IPsec** — via a **PKCS#11** token (tpm2-pkcs11), **not** a PEM
  file; see §3.10 (charon has its own credential subsystem).

`src/completion/list_pki_with_tpm.py` collapses into the normal `pki` completion:
a TPM key is just a `pki` key. Touch points to rework:
`src/conf_mode/interfaces_openvpn.py`, `src/conf_mode/service_ssh.py`,
`src/conf_mode/serial.py`, `src/conf_mode/vpn_ipsec.py`.

### 3.6 Remove enable/disable

- Delete `tpm enable` / `tpm disable` (`op-mode-definitions/tpm.xml.in`,
  `src/op_mode/tpm.py`), the `.tpm.enabled` flag and its `/tmp` RAM cache, and
  the `generate tpm …` definitions (`op-mode-definitions/tpm-pki.xml.in`).
- Collapse `tpm_allowed()` → `tpm_exist()` (present hardware is sufficient);
  retire `tpm_enabled()`.
- **Untouched:** disk/config encryption (`src/helpers/vyos-config-encrypt.py`) —
  separate feature, legitimately early, independent of the flag. The fTPM secure
  storage (`/var/lib/tee`) is also unaffected; only the `boot/.tpm.enabled` flag
  partition is obsoleted (see §3.9).

### 3.7 FIPS interaction

With TPM as a per-key property on the same provider path, the FIPS boundary is
decided per key rather than by a global mode. This removes the "OpenVPN-TPM"
special-case reasoning in the FIPS design and lets `system option fips`
enforcement treat a `storage tpm` key like any other provider-backed key. See
`igos-fips-140-3-design.md` §6.1 for the TPM/FIPS boundary discussion.

### 3.8 Portability & the PCR caveat (operator-visible behavior)

- **Backup/restore:** `config.boot` carries the public cert + `storage tpm`
  reference but **not** the secret. Restoring on different hardware (or after a
  TPM clear) finds no sealed key → the commit must fail with a clear,
  actionable error directing the operator to re-provision via `generate pki …
  storage tpm`. This is correct, expected behavior for hardware-bound keys.
- **PCR binding:** keys sealed to PCRs `4`/`7` are bound to the current
  bootloader + Secure Boot state; changing grub/kernel/SB policy shifts the PCRs
  and unseal fails. This pre-existing property is now surfaced per key rather
  than hidden behind a global mode.

### 3.9 Persistent TPM storage & the enabled-flag partition

There are **two** distinct persistent TPM areas on this platform today; the
redesign affects only one of them.

- **`/var/lib/tee` (`DIR_TPM_REEFS` in `src/op_mode/image_installer.py`)** — the
  fTPM's actual **secure-storage objects**. "REEFS" = *REE FS*, the normal-world
  file system that **OP-TEE** uses to persist secure-world data. This is the
  tell that the "TPM" on this board is a **firmware TPM (fTPM) running in OP-TEE
  TrustZone**, not a discrete chip — which is also why "the TPM is always
  present" is literally true here (it is part of the secure world). This storage
  **must** persist; the installer migrates it into each image's rw overlay on
  upgrade (`boot/<image>/rw/var/lib/tee`). **The redesign does not touch this.**

- **`/dev/mmcblk0p3` → `/run/tpm-state`, holding `boot/.tpm.enabled`
  (`python/vyos/tpm.py`)** — a dedicated raw eMMC partition that holds **only the
  mode flag**, mounted on-demand, read, then unmounted (the dance in
  `tpm_enabled()`). The flag was placed on its own partition — rather than in
  `/config` or an image overlay — for three reasons:

  1. **Image- and reset-independent.** Multiple system images install
     side-by-side under `boot/<image>/…`, and `/config` or an image overlay can
     be wiped on reinstall/config-reset. The flag is a **platform security
     posture**, not per-image config, so it is kept outside any image to survive
     `add system image`, image delete, upgrade, and config reset.
  2. **Chicken-and-egg with config encryption.** The TPM can seal the `/config`
     volume key (`src/helpers/vyos-config-encrypt.py`); a flag that governs TPM
     behavior cannot live inside the very volume whose key is TPM-sealed, since
     it must be readable *before* that volume can be unsealed. A small,
     always-mountable plaintext partition breaks the circular dependency.
  3. **Read-only / measured root.** With Secure Boot + dm-verity the squashfs
     root is immutable and measured, so mutable runtime state cannot be written
     into it; a dedicated partition is a writable home outside the verity tree.

**Effect of the redesign:** removing enable/disable (§3.6) deletes the
`boot/.tpm.enabled` flag and the mount/unmount logic in `tpm_enabled()`, so p3's
only current job disappears. During implementation, confirm whether p3 has any
other role on this board (it appears not to) and whether it can be **retired or
repurposed** once the flag is gone. `/var/lib/tee` and the config-encryption
sealing path are unaffected.

### 3.10 Per-consumer key binding — and why strongSwan needs PKCS#11

`storage` is the single **config-level** source of truth, but the **mechanism
that hands a sealed key to a service differs per consumer**. The consumers fall
into two families:

- **OpenSSL-family consumers** — OpenVPN, serial/stunnel, and (via an agent)
  sshd. These resolve keys through OpenSSL or an agent, so a `storage tpm` key is
  handed over as a provider/engine key reference (OpenSSL tpm2 provider) or an
  `ssh-tpm-agent` key. No change to their credential *model*; just a different
  key handle instead of a PEM.

- **strongSwan / IPsec (charon)** — the odd one out. charon has its **own
  credential subsystem**: `vpn_ipsec.py` extracts the private-key PEM from the
  pki config and writes it to `/etc/swanctl/private/x509_<name>.pem`
  (`wrap_private_key(...)`, lines ~792–811), and charon loads `/etc/swanctl/*`
  into its in-memory credential set. For a `storage tpm` key there is **no
  exportable PEM**, so this path cannot work as-is — strongSwan needs a reference
  into its own credential store that points at the sealed key.

**Decision: strongSwan binds TPM keys via PKCS#11 (tpm2-pkcs11).** Rather than
the native strongSwan `tpm` plugin (which references raw TPM persistent
handles), igOS uses the **`pkcs11` charon plugin** against a **TPM-backed
PKCS#11 token** provided by **`tpm2-pkcs11`** (`libtpm2_pkcs11.so`) layered on
the OP-TEE fTPM / TSS2 stack. Implications:

1. **Build dependency.** `tpm2-pkcs11` (and its TSS2 deps) must be built/packaged
   in `vyos-build`, and the charon `pkcs11` plugin must be present and `load`ed.
   Under FIPS note that `data/templates/ipsec/fips_plugins.conf.j2` disables the
   native crypto plugins and forces IKE primitives through the **openssl**
   plugin; `pkcs11` provides **key storage/operations** (the private-key op runs
   in the TPM), not general crypto, so it must remain loaded and be confirmed as
   not reintroducing non-approved algorithms.
2. **swanctl wiring, not a PEM.** For a `storage tpm` cert/key-pair, `vpn_ipsec.py`
   **skips** the `/etc/swanctl/private/` PEM write and instead registers a
   `pkcs11` module (in `strongswan.conf` `charon.plugins.pkcs11.modules`) and
   references the key by **PKCS#11 URI / object** (token + `CKA_LABEL`/`CKA_ID`)
   from the swanctl connection. The public certificate is still written normally.
3. **Name-as-alias fits.** The pki node name maps to the PKCS#11 object
   **`CKA_LABEL`** on the TPM-backed token. tpm2-pkcs11 manages the underlying TPM
   persistent handles itself, so going through PKCS#11 **avoids** exposing a raw
   persistent handle — which keeps the name-as-alias decision (§3.3, locked #2)
   viable even for strongSwan.
4. **verify()/generate relaxations.** `verify_pki_x509` / `verify_pki_rsa`
   (lines ~259, ~271) currently hard-require `private.key` in the config; they
   must accept its **absence** when `storage tpm` and instead confirm the PKCS#11
   object exists. `generate_pki_*_files` must skip `wrap_private_key` for TPM
   keys and emit the PKCS#11 reference.

> **Decision (2026-11-09) — converge: `tpm2-pkcs11` as the single TPM backend for
> every X.509/TLS consumer**, reached through the OpenSSL **`pkcs11-provider`**
> (and native `pkcs11` for strongSwan), because the provider path is the clear
> industry direction (below) and it yields one uniform, auditable key-op
> boundary. The decision is **subject to the verification gates** at the end of
> this section; if a gate fails, the per-family fallback (tpm2-provider for the
> OpenSSL family) stands. Rationale and research follow.
>
> **First, the crucial distinction — legacy vs. modern paths (rule out the
> legacy ones).** Both OpenVPN and OpenSSL have an *old* key-backend API and a
> *new* one, and the "cautionary notes" you may hear about PKCS#11 almost always
> target the **old** path:
>
> | Stack | Legacy — **avoid** | Modern — **designed-for** |
> |---|---|---|
> | OpenVPN | `--pkcs11-provider` → **pkcs11-helper** (OpenVPN-native, under-maintained) | `--provider` → OpenSSL **provider** mechanism (OpenVPN 2.6+) |
> | OpenSSL | **ENGINE** API: `engine_pkcs11`/libp11 (PKCS#11), `tpm2-tss-engine` (TPM) — deprecated in 3.0, **not FIPS-compatible** | **Provider** API: `pkcs11-provider` (PKCS#11), `tpm2-provider`/tpm2-openssl (TPM) |
>
> The current igOS OpenVPN path already uses the **modern** route
> (`providers default tpm2` in `server.conf.j2` → the **tpm2-provider**), i.e. it
> is already maintainer-aligned. Convergence must **not** reintroduce
> `pkcs11-helper` or the OpenSSL ENGINE: it rides the same **`--provider` /
> provider** mechanism, simply swapping **tpm2-provider → pkcs11-provider**.
>
> **So the real choice is between two OpenSSL *providers*, same provider
> mechanism:**
>
> - **`tpm2-provider` (tpm2-openssl)** — *direct*, one layer (provider → TPM),
>   already in use, keeps the `TSS2 PRIVATE KEY` PEM format igOS already
>   generates; TPM-only.
> - **`pkcs11-provider` + `tpm2-pkcs11`** — *uniform*, two layers (provider →
>   PKCS#11 token → TPM), newer, but the **same backend strongSwan must use** and
>   HSM-portable.
>
> **Feasibility per consumer (assessed 2026-11-09):**
>
> | Consumer | Direct (tpm2-provider) | PKCS#11 (pkcs11-provider/native) |
> |---|---|---|
> | strongSwan | **not possible** (charon doesn't use OpenSSL STORE for keys) | **required** — charon `pkcs11` plugin |
> | OpenVPN | yes (today) | `--provider pkcs11` + `pkcs11:` key URI |
> | serial / stunnel | yes (OpenSSL 3) | OpenSSL `pkcs11-provider` + `pkcs11:` URI |
> | HTTPS / nginx | yes | swap `ssl_certificate_key <file>` for a `pkcs11:` URI |
> | DevID | n/a | own PKCS#11 token (§3.11) |
>
> **strongSwan is the *only* consumer that genuinely requires PKCS#11.** Every
> OpenSSL-family consumer can reach the TPM via the direct tpm2-provider. So
> "converge on PKCS#11" means moving the whole OpenSSL world off the direct
> 1-layer path onto the newer 2-layer stack purely to match strongSwan.
>
> **Genuine exceptions (stay non-PKCS#11 regardless):**
> - **sshd host keys** — OpenSSH has no native PKCS#11 host-key support. Keep
>   **`ssh-tpm-agent`** (TPM-direct; already in use, `src/conf_mode/service_ssh.py`).
> - **WireGuard** — cannot: the kernel WG module needs the raw X25519 scalar;
>   TPM only wraps-the-key-at-rest (separate follow-up, §5).
> - **Disk/config encryption** — stays TPM-direct `tpm2_unseal` in early boot
>   (PKCS#11 in initramfs would be pointless).
>
> **Industry direction (researched 2026-11-09):**
> - **OpenSSL** is moving everything from ENGINEs to **providers**; the ENGINE
>   API is deprecated as of 3.0. Notably **`pkcs11-provider` now lives under the
>   `openssl-projects` GitHub org** (moved from `latchset/`), i.e. it is becoming
>   the de-facto official OpenSSL PKCS#11 connector (targets PKCS#11 3.2,
>   back-compatible to 2.40). **`tpm2-openssl`** is the provider successor to
>   `tpm2-tss-engine` (strictly provider-only, OpenSSL 3.x/4.x, **unchanged TSS2
>   key-file format**).
> - **Red Hat / Fedora / CentOS** are **deprecating OpenSSL ENGINE support**
>   (Fedora "Deprecate OpenSSL engine support"; CentOS 10 leads). Their rationale
>   is directly relevant to us: **"Engines are not FIPS compatible"** and
>   "PKCS#11, TPM already covered by providers." Red Hat employs the
>   `pkcs11-provider` author and backs it as the `engine_pkcs11` replacement.
> - **Takeaway:** the modern *provider* path is the industry direction for
>   **both** PKCS#11 and TPM; **engine-based** access (`engine_pkcs11`,
>   `tpm2-tss-engine`, OpenVPN `pkcs11-helper`) is the thing to avoid — and, per
>   Red Hat, it is **disqualified under FIPS** anyway. Both of our candidates
>   (tpm2-provider, pkcs11-provider) are on the correct side of that line.
>
> **FIPS nuance.** With either provider the private-key operation runs **inside
> the TPM, outside the OpenSSL FIPS module boundary**; a FIPS *claim* must treat
> the TPM as its own validated module or otherwise account for the key-op being
> outside the OpenSSL module. Separately, the **ENGINE** paths are explicitly
> *not* FIPS-compatible (above), so they are ruled out for igOS FIPS regardless.
> See `igos-fips-140-3-design.md`.
>
> **Does convergence make "every key-op approved"?** Only if the TPM itself is a
> FIPS 140-3 **validated** module operated in approved mode. The approval comes
> from **the TPM's validation, not from PKCS#11**: both `pkcs11-provider` and
> `tpm2-provider` perform the private-key op *inside the same TPM*, so neither is
> "more approved." If the TPM is validated, then the private-key ops (in the TPM)
> + all session/bulk crypto (in the OpenSSL FIPS provider) are each performed by a
> validated module in approved mode — no approved function runs outside a
> boundary, which is the compliant target. Convergence's FIPS value is therefore
> **uniformity/auditability** (one key-op boundary for every consumer), not
> approval per se.
>
> **Gating prerequisite — is *this* TPM validatable?** The platform uses an
> **OP-TEE firmware TPM (fTPM)**, not a discrete TPM chip. A discrete TPM usually
> ships with its own CMVP certificate; an fTPM needs its **own** FIPS validation
> (of the fTPM + the secure-world crypto it uses) or must inherit a validated SoC
> crypto module. This is a **substantial, possibly blocking** open question and is
> the real determinant of whether TPM-backed key-ops can be claimed under FIPS —
> independent of PKCS#11 vs tpm2-provider. Additional conditions: operate the TPM
> in approved mode (approved algs/key sizes, RNG/keygen), and confirm
> `tpm2-pkcs11` delegates **all** crypto to the TPM rather than doing any in
> software.
>
> **Trade-off.** Pro (converge, chosen): one backend, one object namespace
> (`CKA_LABEL` = pki node name), one completion, HSM-portable, one uniform FIPS
> key-op boundary, and alignment with the OpenSSL/Red Hat provider direction. Con:
> the OpenSSL family moves off the direct, already-working tpm2-provider onto the
> newer 2-layer `pkcs11-provider` stack. **Fallback if a verification gate
> fails:** per-family — OpenSSL-family on the direct **tpm2-provider**, strongSwan
> (+ DevID) on `tpm2-pkcs11`.
>
> **Caveats to verify before locking:** (a) `pkcs11-provider` maturity + FIPS
> behavior on this platform; (b) that OpenVPN (`--provider`/STORE) and nginx/
> stunnel load a *private key by `pkcs11:` URI* cleanly in practice — the
> tpm2-provider path works today via the TSS2-PEM file.

### 3.11 Device identity (DevID) — independent of operator PKI

A **separate** per-unit identity used only to authenticate the unit to the igOS
cloud (mutual-TLS client identity). It follows the 802.1AR **IDevID** pattern: a
unique TPM-sealed private key with a certificate signed by **our own CA**. It is
**not** a `pki … storage tpm` object and does **not** live in the operator `pki`
tree or operator config — it has a different lifecycle, a different sealing
policy, and must be isolated from operator key management.

**Why independent (the core reasons):**

- **Lifecycle/provenance.** Provisioned once and permanent; must survive config
  reset, image reinstall, and factory-default. Operator PKI keys come and go with
  the configuration.
- **Not in `config.boot`.** If it were a `pki certificate … storage tpm` node an
  operator could delete it, a reset would wipe its reference, and it would ride
  **config backups restored onto other units** — breaking the one-identity-per-
  unit invariant.
- **Upgrade-stable sealing.** It must survive firmware/image upgrades, so it is
  **EK-bound, not sealed to volatile boot-state PCRs** (contrast the service-key
  path, which may bind PCRs 0/2/4/7). A PCR-bound DevID would lose the cloud
  identity on every upgrade.

**Locked decisions (2026-11-09):**

1. **Factory-provisioned.** The DevID keypair is created in the unit's TPM on the
   manufacturing line; the public key is certified by the cloud CA (offline /
   cloud-side) and the resulting DevID certificate + CA trust-anchor are placed
   on the unit. **Not** operator-configurable and **not** created at runtime.
2. **EK-bound.** The DevID key is bound to the TPM **Endorsement Key**, not to
   boot PCRs — giving upgrade/reset/reinstall survivability. EK binding also
   enables **credential-activation** at provisioning, so the CA can verify the
   DevID key resides in *that unit's* genuine TPM before signing.
3. **Isolated store.** Lives in its **own PKCS#11 token** *or* its **own
   dedicated TPM slot/persistent handle**, separate from the operator-key token,
   so operator `generate`/`delete`/commit can never read, overwrite, or remove
   it. Operator-inaccessible.
4. **Cloud channel only.** Used solely by the cloud management/telemetry channel.
   It is **not** referenced from operator config or any service config; the cloud
   agent wires it implicitly. Operators cannot repurpose it for
   OpenVPN/IPsec/SSH/etc.

**On-unit material:** the DevID keypair (TPM-sealed, non-exportable), the DevID
certificate (CA-signed), and the CA certificate (trust anchor). The **CA private
key is cloud-side/offline and never on a unit.**

**Relationship to the rest of the design:** §3.1–§3.10 govern operator-configured
service keys via `storage tpm`; the DevID is a parallel, protected,
factory-provisioned identity. It may share the TPM hardware and the
`tpm2-pkcs11` mechanism, but sits in an isolated token/slot with its own
lifecycle and EK-bound sealing.

**Open / implementation notes:**

- **Factory tooling** — create the DevID in-TPM, generate a CSR, sign with the
  cloud CA, and inject the cert; decide the on-unit home for the DevID cert + CA
  anchor (a protected, upgrade-surviving location such as the TEE secure storage
  `/var/lib/tee` or a dedicated provisioning area — **not** `/config`).
- **EK provenance** — whether units ship with an **EK certificate** to anchor
  credential-activation at the CA.
- **Renewal/rotation** — whether DevID certs are long-lived or renewable (EST
  with the TPM-backed key if re-enrollment is ever needed).

### 3.12 Management-GUI TLS — share the CA, not the DevID key

A tempting shortcut is to reuse the DevID keypair as the management GUI's HTTPS
server certificate (hand customers the public side so their browsers trust the
unit). **Do not reuse the DevID key for this.** The benefit you actually want —
browsers trusting every unit's GUI without warnings — comes from distributing
the **CA** (one trusted root), not from sharing the identity key. Reusing the
DevID key is wrong on four counts:

- **Role mixing (EKU).** DevID is a **client**-auth identity (unit→cloud,
  `clientAuth`); the GUI cert is a **server**-auth identity (browser→unit,
  `serverAuth`). Forcing one key/cert to do both broadens its purpose and some
  stacks reject multi-EKU certs; 802.1AR scopes a DevID to device auth.
- **SAN/hostname mismatch.** Browsers validate the server cert SAN against the
  address the operator typed; a DevID subject is a device identifier
  (serial/EK), not the unit's management hostname/IP — so browsers error. The
  GUI cert needs SANs for how operators reach *that* box, which vary per
  deployment and are not known at factory time.
- **Exposure defeats the isolation.** §3.11 keeps the identity key in an
  isolated, EK-bound store the operator/web stack cannot touch. If the
  public-facing web server signs TLS handshakes with the DevID key, a web-stack
  compromise can request signatures with the device identity key.
- **Lifetime coupling.** DevIDs are long-lived (device lifetime); server certs
  should rotate. Reusing forces one policy on both.

**Recommended pattern (optional feature): issue a separate GUI server cert from
the same CA.**

- Issue a dedicated **TLS server certificate** from the same CA — `serverAuth`
  EKU, SANs matching the management addresses — stored as a normal `pki
  certificate` (optionally `storage tpm` in the **operator** token) and
  referenced by `service https certificates certificate` (the GUI already
  consumes a `pki certificate`; see `src/conf_mode/service_https.py`).
- Use the **DevID only to obtain it**: at first boot the unit authenticates to
  the cloud CA with its DevID (EST) and enrolls the GUI server cert with the
  correct SANs; the DevID authenticates but never serves traffic. (Or pre-issue
  at factory if the management SANs are fixed.)
- Customers install the **CA** as a trusted root → clean HTTPS on every unit.

Net: the **trust anchor** (your CA) is shared across the cloud channel and the
browser GUI, while **keys/certs stay separate per role** — preserving DevID
isolation and plugging the GUI cert into the existing `pki certificate` +
`storage tpm` plumbing.

## 4. Locked decisions (2026-11-09)

1. **CA keys included** — `storage tpm` is available on `pki ca … private` as
   well as `certificate` and `key-pair`.
2. **Binding = name-as-alias** — the node name is the TPM object alias; explicit
   handle leaf deferred.
3. **No migration** — greenfield design; there is no deployed TPM-PKI config to
   fold in. (If any lab unit has old `/config/auth/tpm/*` state, it is
   re-provisioned, not migrated.)
4. **Enable/disable removed** — TPM is always-present hardware; no mode switch,
   no reboot.
5. **WireGuard is a follow-up** — mirror the same `…private-key storage tpm`
   model under `interfaces wireguard` after the `pki` core lands (different
   subtree; keeps the first change focused).
6. **strongSwan binds TPM keys via PKCS#11** — use the charon `pkcs11` plugin
   against a `tpm2-pkcs11` token (not native strongSwan `tpm` handles, not a PEM
   in `/etc/swanctl/private/`); see §3.10.
7. **Device identity (DevID) is separate** — factory-provisioned, EK-bound,
   isolated token/slot, cloud-channel-only, outside the operator `pki` tree; see
   §3.11.
8. **GUI TLS shares the CA, not the DevID key** — the management-GUI HTTPS cert
   is a *separate* `serverAuth` cert issued from the same CA (optionally enrolled
   via the DevID), referenced as a normal `pki certificate`; the DevID key is
   never reused to serve traffic. Optional feature; see §3.12.
9. **Converge on PKCS#11 (target architecture)** — all X.509/TLS consumers reach
   the TPM through `tpm2-pkcs11` (OpenSSL `pkcs11-provider`; native `pkcs11` for
   strongSwan), per §3.10. Chosen for a single uniform/auditable key-op boundary
   and alignment with the OpenSSL/Red Hat engine→provider direction. **Subject to
   the §3.10 verification gates**; per-family (tpm2-provider for the OpenSSL
   family) is the fallback. Engine paths (`engine_pkcs11`, `tpm2-tss-engine`,
   OpenVPN `pkcs11-helper`) are ruled out.

- **PKCS#11 convergence — decided (§3.10, decision #9); remaining gates.** The
  direction is set (converge via `pkcs11-provider`/`tpm2-pkcs11`). Before it can
  be relied on, close these gates: (a) **fTPM FIPS validatability** — whether the
  OP-TEE firmware TPM can be CMVP-validated / operated in approved mode (the real
  blocker for any FIPS claim on TPM key-ops); (b) `pkcs11-provider` maturity +
  FIPS behavior on this platform; (c) that OpenVPN (`--provider`/STORE), nginx,
  and stunnel load a private key by `pkcs11:` URI cleanly; (d) that `tpm2-pkcs11`
  delegates all crypto to the TPM (no software crypto). If a gate fails, fall
  back to per-family (tpm2-provider for the OpenSSL family).
- **`verify()` error ergonomics** — precise messages for: `storage tpm` with a
  stray `private key`; `password-protected` under TPM; and missing sealed key on
  restore/different hardware.
- **`generate pki` UX** — surface `storage tpm` as an option/flag consistently
  across `certificate`, `key-pair`, `ca`, and self-signed vs CSR flows.
- **Retire/repurpose `/dev/mmcblk0p3`** — once the `boot/.tpm.enabled` flag is
  removed (§3.6, §3.9), confirm p3 has no other role and decide whether to retire
  or repurpose the partition. The OP-TEE secure storage (`/var/lib/tee`) and
  config-encryption sealing are unaffected.

## 6. Why no migration (explicit)

This is a new igOS capability; there is no released configuration that references
TPM keys through the `pki` tree, because today TPM keys are **not** in the config
at all — they are files under `/config/auth/tpm/*` selected by a runtime flag.
There is therefore nothing in `config.boot` to transform, and no `pki`
`syntaxVersion` bump is required. Any pre-existing on-disk TPM material from
development units is handled by **re-provisioning** (`generate pki … storage
tpm`), not by an automated migration.
