# igOS TPM-PKI Integration — Design Sketch

Status: **Design — no code yet (2026-11-09)**

Scope: fold TPM-backed private keys into the normal `pki` configuration tree so
operators do **all** PKI work in **one place**, whether a key is held in software
or sealed in the TPM. TPM stops being a global, reboot-gated *mode* with its own
parallel key store and becomes a per-key **storage attribute**
(`storage software | tpm`). The TPM is treated as always-present hardware; there
is no enable/disable. This is a **greenfield** redesign for igOS — there is no
deployed TPM-PKI configuration to preserve, so **no migration** is required.

This is the counterpart to `docs/igos-fips-140-3-design.md`: FIPS already set the
precedent that a security capability belongs in the **configuration** (`set
system option fips`), applied by commit, visible in `show configuration`, and
enforced per-feature — not hidden behind an out-of-band op-mode toggle.

---

## 1. Motivation — what's wrong with the current model

Two structural problems, both confirmed in the code (2026-11-09):

### 1.1 Activation is an out-of-band op-mode toggle that forces a reboot

- `tpm enable` / `tpm disable` (`op-mode-definitions/tpm.xml.in`) call
  `src/op_mode/tpm.py`, which in `python/vyos/tpm.py` just `touch`/`rm` a flag
  file `/run/tpm-state/boot/.tpm.enabled` on a mounted persistent partition and
  then **unconditionally reboot** the box.
- That state lives **outside the configuration tree**: invisible to `show
  configuration`, never written to `config.boot`, not diffable, not captured in a
  backup, not restored when a config is loaded onto another unit.
- The reboot is **not** a hardware or crypto requirement. The TPM is a passive
  chip that measures boot state into PCRs on every boot regardless of any VyOS
  setting; `tpm_enable()` performs no crypto and touches no hardware. Every
  consumer of the flag is a **conf-mode (commit-time)** script — so the reboot
  exists only to force the normal boot-time config replay to re-run those
  scripts and restart dependent services. A commit could do the same live.

### 1.2 Key management is a parallel store keyed off a hidden global flag

- TPM keys are generated by `generate tpm …` (op-mode) and written as **files**
  under `/config/auth/tpm/…` (`python/vyos/tpm_pki.py` → `TPM_PKI_ROOT_PATH =
  /config/auth/tpm`), **not** as `pki` config nodes.
- Consumers branch on the global `tpm_enabled()` flag. In
  `src/conf_mode/interfaces_openvpn.py`, when `tpm_enabled()` it **ignores the
  `pki certificate` tree entirely** and reads
  `/config/auth/tpm/cert/<name>/<name>.pem|.key` instead; otherwise it uses the
  normal PKI nodes. `src/conf_mode/service_ssh.py` and `src/conf_mode/serial.py`
  branch the same way.
- The tell is `src/completion/list_pki_with_tpm.py`: the **same** CLI completion
  returns TPM-store names when `tpm_enabled()`, and `pki certificate` names
  otherwise.

Net effect: the same config reference (`certificate foo`) silently resolves to a
**different backing store** depending on a reboot-persisted flag that is not in
the config. Two parallel universes, non-local reasoning, no single source of
truth, and config portability quietly breaks.

### 1.3 Who actually needs "TPM at boot"? (grounding the greenfield claim)

The only consumer of the PCR-sealed key primitives (`write_tpm_key` /
`read_tpm_key` / `clear_tpm_key` in `python/vyos/tpm.py`) is **disk/config
encryption** (`src/helpers/vyos-config-encrypt.py`), which seals the `/config`
volume key to PCRs `0,2,4,7` and unseals it in early boot to mount the encrypted
volume. That feature:

- is a **system disk-encryption** concern, not a PKI object the operator
  manages;
- **does not use the `.tpm.enabled` flag** — it checks `/sys/class/tpm/tpm0`
  directly and has its own enable flow;
- never touches the `pki` tree.

Everything else TPM-related is **config/commit-driven**, not early-boot:
OpenVPN/SSH/serial PKI objects (the `tpm_pki` store) and the WireGuard
file-wrapped private key (`src/op_mode/pki.py` `write_tpm_key_file` ↔
`src/conf_mode/interfaces_wireguard.py` `read_tpm_key_file`). The installer
(`src/op_mode/image_installer.py`) only *copies* the TPM state dir on upgrade; it
seals nothing.

**Conclusion:** the global enable/disable flag serves no early-boot or non-config
purpose. It exists solely to flip the conf-mode PKI consumers between the two
stores. Remove it; make TPM a per-key attribute. Disk encryption is orthogonal
and stays exactly as-is.

## 2. Goal & principles

1. **One place for PKI.** An operator configures `pki certificate`, `pki
   key-pair`, and `pki ca` the same way regardless of where the private key
   lives. TPM is a property of the key, surfaced as `storage tpm`.
2. **No global mode, no reboot.** The TPM is always present. There is no
   enable/disable; changes apply on commit like any other config.
3. **Secrets never in config.** A `storage tpm` key's private material stays
   sealed in the TPM; `config.boot` carries only the public certificate and the
   `storage tpm` reference. (This is strictly *better* than software keys, whose
   PEM is in the config.)
4. **Single source of truth.** Consumers resolve a `pki` node and read its
   `storage`; they never consult a hidden global flag. CLI completion is unified.
5. **Explicit FIPS boundary.** TPM key operations ride the same OpenSSL provider
   path as everything else, so FIPS reasoning is per-key and explicit (see
   `igos-fips-140-3-design.md` §6.1).

## 3. Design

### 3.1 Schema — `storage` on the `private` node

New include `interface-definitions/include/pki/private-key-storage.xml.i`:

```xml
<leafNode name="storage">
  <properties>
    <help>Backing store for the private key</help>
    <completionHelp><list>software tpm</list></completionHelp>
    <valueHelp>
      <format>software</format>
      <description>Private key stored in the configuration (PEM)</description>
    </valueHelp>
    <valueHelp>
      <format>tpm</format>
      <description>Private key sealed in the TPM; not present in the configuration</description>
    </valueHelp>
    <constraint><regex>(software|tpm)</regex></constraint>
  </properties>
  <defaultValue>software</defaultValue>
</leafNode>
```

Wired into the three asymmetric key holders in
`interface-definitions/pki.xml.in`:

- `pki certificate <name> private` (currently ~line 111)
- `pki key-pair <name> private` (~line 155)
- `pki ca <name> private` (~line 19) — **CA signing key in the TPM is a primary
  use case; included.**

Left out: `pki openssh`, `pki dh`, `pki openvpn shared-secret` — not
TPM-sealable asymmetric keys.

### 3.2 Semantics

- `storage software` (default) → unchanged behavior: the existing `private key
  <base64 PEM>` leaf
  (`interface-definitions/include/pki/cli-private-key-base64.xml.i`) holds the
  key.
- `storage tpm` → the `private key` leaf is **absent**. The public
  `certificate` leaf still lives in the node, so the certificate is in config and
  portable. `src/conf_mode/pki.py` `verify()` enforces:
  - `storage tpm` ⇒ no `private key` set (mutually exclusive), and
  - `password-protected` is rejected under `storage tpm` (meaningless for a
    sealed key).

### 3.3 Binding — name-as-alias

The tagNode **name** *is* the TPM object alias: `pki certificate foo private
storage tpm` binds to the TPM object `foo`. One-to-one, zero extra config, and it
matches how the current store already keys blobs by name
(`/config/auth/tpm/.../<name>`). An explicit `tpm-handle` / `tpm-index` leaf for
advanced persistent-handle control is a possible later addition, not part of the
initial design.

### 3.4 Generation — one command, a flag

Fold TPM into the existing `generate pki …` flow (which already prints `set`
commands for the operator to apply). For example:

```
generate pki certificate <name> … storage tpm
```

seals the key into the TPM (under alias `<name>`) and emits:

```
set pki certificate <name> private storage tpm
set pki certificate <name> certificate <base64 public cert>
```

instead of a base64 private key. The legacy `generate tpm …` op-mode path is
removed.

### 3.5 Consumers — resolve the node, not a global flag

Every `if tpm_enabled(): <parallel path>` is replaced by: resolve the referenced
`pki` node and read `private storage`. If `tpm`, hand the service its TPM-backed
key:

- **OpenVPN / serial / stunnel** — via the OpenSSL tpm2 provider path.
- **sshd** — via `ssh-tpm-agent` with the sealed host key.

`src/completion/list_pki_with_tpm.py` collapses into the normal `pki` completion:
a TPM key is just a `pki` key. Touch points to rework:
`src/conf_mode/interfaces_openvpn.py`, `src/conf_mode/service_ssh.py`,
`src/conf_mode/serial.py`.

### 3.6 Remove enable/disable

- Delete `tpm enable` / `tpm disable` (`op-mode-definitions/tpm.xml.in`,
  `src/op_mode/tpm.py`), the `.tpm.enabled` flag and its `/tmp` RAM cache, and
  the `generate tpm …` definitions (`op-mode-definitions/tpm-pki.xml.in`).
- Collapse `tpm_allowed()` → `tpm_exist()` (present hardware is sufficient);
  retire `tpm_enabled()`.
- **Untouched:** disk/config encryption (`src/helpers/vyos-config-encrypt.py`) —
  separate feature, legitimately early, independent of the flag. The fTPM secure
  storage (`/var/lib/tee`) is also unaffected; only the `boot/.tpm.enabled` flag
  partition is obsoleted (see §3.9).

### 3.7 FIPS interaction

With TPM as a per-key property on the same provider path, the FIPS boundary is
decided per key rather than by a global mode. This removes the "OpenVPN-TPM"
special-case reasoning in the FIPS design and lets `system option fips`
enforcement treat a `storage tpm` key like any other provider-backed key. See
`igos-fips-140-3-design.md` §6.1 for the TPM/FIPS boundary discussion.

### 3.8 Portability & the PCR caveat (operator-visible behavior)

- **Backup/restore:** `config.boot` carries the public cert + `storage tpm`
  reference but **not** the secret. Restoring on different hardware (or after a
  TPM clear) finds no sealed key → the commit must fail with a clear,
  actionable error directing the operator to re-provision via `generate pki …
  storage tpm`. This is correct, expected behavior for hardware-bound keys.
- **PCR binding:** keys sealed to PCRs `4`/`7` are bound to the current
  bootloader + Secure Boot state; changing grub/kernel/SB policy shifts the PCRs
  and unseal fails. This pre-existing property is now surfaced per key rather
  than hidden behind a global mode.

### 3.9 Persistent TPM storage & the enabled-flag partition

There are **two** distinct persistent TPM areas on this platform today; the
redesign affects only one of them.

- **`/var/lib/tee` (`DIR_TPM_REEFS` in `src/op_mode/image_installer.py`)** — the
  fTPM's actual **secure-storage objects**. "REEFS" = *REE FS*, the normal-world
  file system that **OP-TEE** uses to persist secure-world data. This is the
  tell that the "TPM" on this board is a **firmware TPM (fTPM) running in OP-TEE
  TrustZone**, not a discrete chip — which is also why "the TPM is always
  present" is literally true here (it is part of the secure world). This storage
  **must** persist; the installer migrates it into each image's rw overlay on
  upgrade (`boot/<image>/rw/var/lib/tee`). **The redesign does not touch this.**

- **`/dev/mmcblk0p3` → `/run/tpm-state`, holding `boot/.tpm.enabled`
  (`python/vyos/tpm.py`)** — a dedicated raw eMMC partition that holds **only the
  mode flag**, mounted on-demand, read, then unmounted (the dance in
  `tpm_enabled()`). The flag was placed on its own partition — rather than in
  `/config` or an image overlay — for three reasons:

  1. **Image- and reset-independent.** Multiple system images install
     side-by-side under `boot/<image>/…`, and `/config` or an image overlay can
     be wiped on reinstall/config-reset. The flag is a **platform security
     posture**, not per-image config, so it is kept outside any image to survive
     `add system image`, image delete, upgrade, and config reset.
  2. **Chicken-and-egg with config encryption.** The TPM can seal the `/config`
     volume key (`src/helpers/vyos-config-encrypt.py`); a flag that governs TPM
     behavior cannot live inside the very volume whose key is TPM-sealed, since
     it must be readable *before* that volume can be unsealed. A small,
     always-mountable plaintext partition breaks the circular dependency.
  3. **Read-only / measured root.** With Secure Boot + dm-verity the squashfs
     root is immutable and measured, so mutable runtime state cannot be written
     into it; a dedicated partition is a writable home outside the verity tree.

**Effect of the redesign:** removing enable/disable (§3.6) deletes the
`boot/.tpm.enabled` flag and the mount/unmount logic in `tpm_enabled()`, so p3's
only current job disappears. During implementation, confirm whether p3 has any
other role on this board (it appears not to) and whether it can be **retired or
repurposed** once the flag is gone. `/var/lib/tee` and the config-encryption
sealing path are unaffected.

## 4. Locked decisions (2026-11-09)

1. **CA keys included** — `storage tpm` is available on `pki ca … private` as
   well as `certificate` and `key-pair`.
2. **Binding = name-as-alias** — the node name is the TPM object alias; explicit
   handle leaf deferred.
3. **No migration** — greenfield design; there is no deployed TPM-PKI config to
   fold in. (If any lab unit has old `/config/auth/tpm/*` state, it is
   re-provisioned, not migrated.)
4. **Enable/disable removed** — TPM is always-present hardware; no mode switch,
   no reboot.
5. **WireGuard is a follow-up** — mirror the same `…private-key storage tpm`
   model under `interfaces wireguard` after the `pki` core lands (different
   subtree; keeps the first change focused).

## 5. Open items / follow-ups

- **WireGuard** (`interfaces wireguard … private-key`) carries its own
  file-wrapped TPM key today (`src/op_mode/pki.py` `write_tpm_key_file` ↔
  `src/conf_mode/interfaces_wireguard.py` `read_tpm_key_file`). Apply the same
  per-key `storage` model there as a separate change.
- **Provider plumbing specifics** — exact OpenSSL tpm2-provider / `ssh-tpm-agent`
  wiring per consumer (OpenVPN, serial/stunnel, sshd) to be detailed when code
  work starts.
- **`verify()` error ergonomics** — precise messages for: `storage tpm` with a
  stray `private key`; `password-protected` under TPM; and missing sealed key on
  restore/different hardware.
- **`generate pki` UX** — surface `storage tpm` as an option/flag consistently
  across `certificate`, `key-pair`, `ca`, and self-signed vs CSR flows.
- **Retire/repurpose `/dev/mmcblk0p3`** — once the `boot/.tpm.enabled` flag is
  removed (§3.6, §3.9), confirm p3 has no other role and decide whether to retire
  or repurpose the partition. The OP-TEE secure storage (`/var/lib/tee`) and
  config-encryption sealing are unaffected.

---

## 6. Why no migration (explicit)

This is a new igOS capability; there is no released configuration that references
TPM keys through the `pki` tree, because today TPM keys are **not** in the config
at all — they are files under `/config/auth/tpm/*` selected by a runtime flag.
There is therefore nothing in `config.boot` to transform, and no `pki`
`syntaxVersion` bump is required. Any pre-existing on-disk TPM material from
development units is handled by **re-provisioning** (`generate pki … storage
tpm`), not by an automated migration.
